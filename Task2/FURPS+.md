# FURPS+: онлайн-депозиты (MVP) и онлайн-кредиты

Требования собраны из описания задания и IT-ландшафта банка «Стандарт». Депозиты рассматриваются в объёме MVP на 6 месяцев, кредиты — как решение на горизонте года. ИБ — интернет-банк, БКИ — бюро кредитных историй.

Архитектурно значимые требования собраны в группе +R по четырём видам ограничений: проектирования, реализации, интерфейсов и физическим. Пометка **Дополнительное** в поле «Комментарий» означает, что требования нет в задании; там же его обоснование.

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | Функциональные (Functionality) | |
| F1 | **Сайт, депозит.** Новый клиент видит список доступных депозитов с актуальными ставками | |
| F2 | **Сайт, депозит.** Клиент подаёт заявку на депозит, указав номер телефона и Ф. И. О. Заявка попадает в систему кол-центра | |
| F3 | **Кол-центр, депозит.** Менеджер кол-центра видит в своей системе заявку с сайта и ставки по депозитам, звонит клиенту и может предложить особые условия | |
| F4 | **Отделение, депозит.** После звонка новый клиент приходит в отделение для идентификации, и депозит открывается там | Банк не может принять нового клиента без личной проверки документов |
| F5 | **ИБ, депозит.** Клиент видит список доступных депозитов и накопительных счетов с актуальными ставками, а также персональные ставки лично для него | Накопительные счета — из целей бизнеса: через 6 месяцев клиент открывает в ИБ депозит или накопительный счёт |
| F6 | **ИБ, депозит.** Клиент указывает счёт и сумму и подаёт заявку на открытие депозита или накопительного счёта | |
| F7 | **ИБ.** Заявки на депозит и на кредит клиент подтверждает СМС-кодом | |
| F8 | **Бэк-офис, депозит (MVP).** Заявка из ИБ попадает в АБС. Менеджер бэк-офиса обрабатывает её по текущему процессу и подтверждает условия депозита в АБС | Открытие депозита без бэк-офиса — цель на год (S2) |
| F9 | **Ставки.** Ставки по депозитам ведутся в информационной системе, а не в Excel-файлах. С ними работают бэк-офис депозитов и бэк-офис кредитов. Согласование ставки по заявке, в том числе специальной, тоже идёт в системе, а не по почте | Бизнес предлагает вести ставки и согласование в АБС. Как это сочетается с перегрузкой АБС — в +R7 |
| F10 | **Уведомления.** Клиент получает СМС:<br>— после подтверждения ставки и после открытия депозита;<br>— после подачи заявки на кредит на сайте: прийти в отделение для идентификации и получения кредита;<br>— при каждом изменении статуса заявки на кредит | |
| F11 | **Сайт, кредит.** Новый клиент видит предложение кредита со ставкой. Условия кредитов берутся из Кредитного конвейера | |
| F12 | **Сайт, кредит.** Клиент подаёт заявку на кредит, указав телефон и Ф. И. О. Если он заполнит ещё и паспортные данные, то сразу получает предварительное решение: одобрен кредит или нет | О новом клиенте банк ничего не знает, поэтому скоринг опирается только на общие данные БКИ |
| F13 | **Отделение, кредит.** Менеджер в отделении находит заявку клиента с сайта и продолжает работать с ней. Для полностью нового клиента он создаёт новую заявку в АБС | |
| F14 | **ИБ, кредит.** Клиент видит список кредитов с актуальными условиями, как на сайте, и своё предодобренное предложение, если по нему уже был скоринг | |
| F15 | **ИБ, кредит.** Клиент указывает счёт зачисления и данные заявки и отправляет заявку в банк. Если ситуация клиента изменилась, скоринг повторяется по упрощённой процедуре | |
| F16 | **ИБ.** Клиент видит статус своей заявки на депозит или кредит | **Дополнительное:** в MVP заявку вручную обрабатывает бэк-офис, на это уходит время. Без статуса в ИБ клиент будет звонить в кол-центр, а кол-центр и так рискует не справиться с потоком звонков |
| F17 | **Безопасность.** Данные шифруются при передаче (HTTPS/TLS): между браузером и сайтом, между браузером и ИБ, между новыми сервисами | По FURPS безопасность относится к функциональности. С сайта приходят чувствительные данные: Ф. И. О., телефон, паспорт |
| F18 | **Безопасность.** Сотрудники депозитов и сотрудники кредитов не имеют доступа к данным друг друга, хотя и те и другие работают со ставками. Доступ выдаётся по ролям | Требование безопасности из описания процесса открытия депозита (задание 1) |
| F19 | **Аудит.** Изменения ставок и решения по заявкам записываются в журнал: кто, когда и что изменил | **Дополнительное:** ставка напрямую влияет на деньги банка, а работать со ставками будут два подразделения. Журнал нужен, чтобы разбирать ошибки и проходить проверки |
| U | Удобство использования (Usability) | |
| U1 | Интерфейс максимально удобен для клиента: заявка подаётся онлайн за несколько шагов, без визита в отделение. Исключение — идентификация нового клиента (F4) | |
| U2 | Сайт, ИБ и новые интерфейсы следуют системе дизайна банка: пользователь видит привычные цвета и брендированные элементы | |
| U3 | Сайт и ИБ удобны на смартфоне и понятны возрастным клиентам: крупный шрифт, простые формулировки, подсказки на каждом шаге | **Дополнительное:** банк хочет привлечь молодых клиентов, а они чаще пользуются смартфоном. Основные клиенты — люди старшего возраста: если онлайн им непонятно, они звонят в кол-центр |
| U4 | Сотрудники работают с онлайн-заявками в привычных системах: бэк-офис и отделения — в АБС, операторы — в системе кол-центра | **Дополнительное:** 500 сотрудников отделений и 200 операторов не придётся переучивать на новые рабочие места |
| R | Надёжность (Reliability) | |
| R1 | Режим работы 24/7, доступность всех сервисов 99,9%: не больше 8 ч 46 мин простоя в год | |
| R2 | ИБ и новые сервисы остаются доступны при сбое ЦОД и выдерживают требуемую нагрузку | **Конфликт.** Команда ИБ считает требование пока невыполнимым: всё работает на одной группе серверов в одном ЦОД, онлайн-клиентов мало, и даже день простоя некритичен. Компромисс — в +R14 |
| R3 | Заявка, которую клиент подтвердил, не теряется и не дублируется. Если АБС, скоринг или СМС-шлюз недоступны или перегружены, заявка всё равно принимается и обрабатывается, когда система восстановится | **Дополнительное:** клиент уже подтвердил операцию СМС-кодом, и потерять заявку нельзя. Обмен с АБС будет асинхронным (+R10), а значит, сообщения должны доходить гарантированно |
| P | Производительность (Performance) | |
| P1 | Отклик по всем операциям сайта и ИБ — миллисекунды: 95% запросов быстрее 500 мс. Это касается и справочных данных, которые сейчас при проведении платежей загружаются дольше секунды | Порог 500 мс предлагаю я: «миллисекунды» в исходном требовании не проверить |
| P2 | Сервисы масштабируются горизонтально, запросы равномерно распределяются между серверами, приложениями и ЦОД | АБС так масштабироваться не может, только вертикально (+R6) |
| P3 | Решение по заявке на кредит из ИБ или с сайта принимается в течение одного дня, если данных достаточно. Заявки по предодобренным предложениям сотрудники обрабатывают в тот же рабочий день | Сейчас заявки попадают в Кредитный конвейер раз в сутки, поэтому нужно +R9 |
| P4 | Предварительное решение по кредиту на сайте клиент получает сразу после ввода паспортных данных, не дольше чем за 30 секунд | Порог 30 секунд предлагаю я |
| P5 | Новая ставка появляется на сайте, в ИБ и в системе кол-центра не позднее чем через 5 минут после изменения | **Дополнительное:** ставки меняются каждый день, и клиенту нельзя показать устаревшую. С таким требованием онлайн-каналы могут читать ставки из копии, а не из АБС (+R7) |
| S | Поддерживаемость (Supportability) | |
| S1 | Для дальнейшего расширения системы ведётся документация: спецификации API (OpenAPI) и событий (AsyncAPI), ADR, C4-диаграммы | Требование есть в задании, состав документации предлагаю я |
| S2 | MVP развивается до цели на год без переделки: депозит открывается автоматически без бэк-офиса, в отделении работает только фронт-офис, заявки на кредит подаются онлайн | **Дополнительное:** это цели бизнеса на год. Ручное согласование в MVP должно быть отдельным шагом процесса, который потом заменяется автоматическим правилом |
| S3 | Новые продукты подключаются к тем же сервисам заявок, ставок и уведомлений, без отдельной интеграции с АБС под каждый продукт | **Дополнительное:** команда АБС опасается онлайн-заявок «на большое количество продуктов». Общие сервисы сдерживают и нагрузку на АБС, и стоимость доработок |
| S4 | Новые сервисы и интеграции под мониторингом: метрики, логи, трассировка запросов, оповещения о сбоях | **Дополнительное:** без мониторинга доступность 99,9% (R1) нельзя ни обеспечить, ни подтвердить |
| S5 | Интеграции с АБС, системой кол-центра, Кредитным конвейером и скорингом проверяются интеграционными тестами на тестовых стендах этих систем | **Дополнительное:** каждая заявка проходит через несколько систем, и без интеграционных тестов ошибку на стыке клиент увидит первым |
| +R | + Ограничения (Restrictions) | |
| | *Ограничения проектирования: технологии и средства разработки* | |
| +R1 | Используются технологии, которые уже есть в банке: БД MS SQL, Oracle, PostgreSQL. Новые технологии должны быть совместимы с текущими платформами разработки, и в банке должна быть экспертиза хотя бы на уровне языка: .NET — у команды ИБ, Java — у команды АБС и в Кредитном конвейере, Python — в скоринге | |
| +R2 | Брокер сообщений — Kafka. Текущая платформа ИБ с Kafka несовместима, поэтому ИБ работает с ней через отдельный сервис | |
| +R3 | Ядро ИБ не дорабатывается. ИБ — монолит на платформе подрядчика (ASP.NET MVC 4.5, .NET Framework 4.5, MS SQL), и работа с СМС реализована в ядре. Новую функциональность, включая СМС-подтверждение, команда банка делает вне ядра | Изменения ядра привязаны к подрядчику, бизнес просит их избегать |
| +R4 | Систему кол-центра и Кредитный конвейер банк дорабатывает сам: систему кол-центра — Java-специалисты команды АБС через механизмы расширения платформы, процессы и обработчики конвейера на Camunda — IT-отдел | Обе системы сопровождают подрядчики, но в банке есть нужная экспертиза |
| | *Ограничения реализации: требования к архитектуре* | |
| +R5 | Функциональность открытия депозитов делается отдельными сервисами рядом с монолитом ИБ. Это первый шаг перевода ИБ на микросервисы, пока только для депозитов. Сервисы не хранят состояние на сервере и масштабируются горизонтально (P2) | В задании предложено «подумать о переводе интернет-банка на микросервисную архитектуру, но пока только в рамках задачи открытия депозитов» |
| +R6 | В новых процессах ни ИБ, ни сайт не работают с АБС напрямую — ни через API, ни через её БД | БД АБС перегружена, а сама АБС масштабируется только вертикально. Онлайн-нагрузка не должна доходить до неё синхронно |
| +R7 | Ставки ведутся в одной системе. Сайт, ИБ и система кол-центра читают ставки, а ИБ ещё и данные клиента для персональных ставок, из своей копии вне АБС | Бизнес предлагает вести ставки в АБС. Работа сотрудников со ставками почти не нагружает её БД, а онлайн-запросы клиентов нагрузили бы. Копия обновляется не реже P5 |
| +R8 | Скоринг не нагружается предрасчётами: предодобренные предложения строятся по сохранённым результатам прошлых скорингов | В рабочие часы скоринг и так испытывает повышенную нагрузку |
| +R9 | Онлайн-заявки на кредит передаются в Кредитный конвейер напрямую, минуя АБС | Обмен АБС → конвейер через БД раз в сутки ускорить нельзя, а решение нужно в тот же день (P3). Конвейер масштабируется горизонтально и работает 24/7 |
| | *Требования к интерфейсам: протоколы и способы взаимодействия* | |
| +R10 | Новые сервисы обмениваются с АБС асинхронно, через Kafka: доставка гарантирована, повторная обработка сообщения не создаёт дублей | Так выполняются +R6 и R3 |
| +R11 | Сайт, ИБ и система кол-центра вызывают новые сервисы синхронно по REST API поверх HTTPS. Изменения ставок и статусов заявок рассылаются событиями через Kafka | ИБ подключить к Kafka нельзя (+R2), поэтому он работает только по REST |
| +R12 | Предварительное решение по кредиту на сайте — синхронная цепочка REST-вызовов «сайт → скоринг → БКИ» | Скоринг и БКИ уже работают по REST API |
| +R13 | Все СМС отправляются через СМС-шлюз банка | |
| | *Физические ограничения: инфраструктура* | |
| +R14 | Банк использует два ЦОД — основной и резервный. Новые сервисы и их данные развёрнуты в обоих. Монолит ИБ на время MVP работает в одном ЦОД с переключением на резервный, а к цели на год — в обоих одновременно | Компромисс в конфликте R2: требование бизнеса выполняется для нового, а ИБ доводится до него к росту числа онлайн-клиентов |
| +R15 | Персональные данные клиентов (Ф. И. О., телефон, паспорт) хранятся только в инфраструктуре банка, по 152-ФЗ «О персональных данных» | **Дополнительное:** с сайта приходят паспортные данные новых клиентов, а закон ограничивает, где их хранить и кто может их видеть |
